# Runtime audit: doc2pdf 1.2.0 / DocPress

Audit date: 2026-10-19. Baseline: `c8df165597d8a792b454d1b8c5ddc5b5d95ef219`.

The extension contains a working browser-to-raster-PDF pipeline, but the tested release is **not reliable on the two live documents shipped in its own test suite**. Controlled browser fixtures produce real, readable PDFs. Clicking the unchanged export control on publicly visible first pages encounters an image-loading failure, even while the shipped live test reports success. No functional source changes were made for this audit.

The project was renamed to DocPress separately during the audit. Findings refer to the baseline runtime files, whose behavior was not changed by that rename.

## Findings

### High: credentialed image XHR prevents export of ordinary public CDN images

Source: [content.js:326](https://github.com/nguyenquan27122005-cmd/docpress/blob/c8df165597d8a792b454d1b8c5ddc5b5d95ef219/content.js#L326), especially `xhr.withCredentials = true` at line 338, and the mandatory `inlineImages` call at line 537.

The actual export pipeline fetches every remote `img`/`srcset` candidate with a credentialed XHR before rendering. Public CDNs commonly return `Access-Control-Allow-Origin: *`. Chromium rejects that response when credentials mode is `include`.

On the public Scribd sample `https://www.scribd.com/document/1055407232/CV-Factory-Manager`, the first page is visibly rendered in a fresh, signed-out browser. Its image request returns HTTP 200 with `Access-Control-Allow-Origin: *`; CDP records `corsError: WildcardOriginNotAllowed`. Clicking the injected, unchanged extension control for page 1 reports:

> Trang 1: Không tải được ảnh. Thử phạm vi ngắn hơn hoặc chất lượng thấp hơn.

No PDF is downloaded. Lowering quality or selecting a shorter range cannot solve this CORS policy mismatch. Unlike HTML fetching, the image path has no background bridge fallback. A controlled actual-extension fixture with an HTTP 200 image and the same wildcard response reproduces the failure.

The public Studocu sample also reached the same image-error status. An independent rerun reproduced actual export failures on both public targets while the shipped custom PDF probes still passed. Some navigation attempts were intermittently interrupted, and the saved network trace identifies the precise wildcard-CORS root cause for Scribd. This audit does not generalize those two samples to every document on either provider.

Evidence: `scribd-live-network.json`, `real-export-test.log`, `scribd-live-chrome-source.png`, and the `scribd-wildcard-image` case in `runtime-results.json`.

### Medium: missing Studocu page dimensions silently crop the exported document

Source: [content.js:219](https://github.com/nguyenquan27122005-cmd/docpress/blob/c8df165597d8a792b454d1b8c5ddc5b5d95ef219/content.js#L219) and [content.js:505](https://github.com/nguyenquan27122005-cmd/docpress/blob/c8df165597d8a792b454d1b8c5ddc5b5d95ef219/content.js#L505).

Studocu extraction copies only `row.width` and `row.height`. If they are absent, rendering uses 794 x 1123 CSS pixels and an `overflow:hidden` page container. It does not measure the provider wrapper or loaded background image.

An actual-extension fixture whose page HTML is 1000 x 1400 CSS pixels, with no explicit dimensions on the row, downloads a valid PDF of only 595.5 x 842.25 points, equivalent to 794 x 1123 CSS pixels. Text and a green marker placed at the bottom right are missing. The widget reports `Đã tải PDF`.

This is a relevant provider shape: the public Studocu sample's real rows contained only `pageHtml`, `pageHtmlWrapper`, and `pageNumber`; its visible background image was 1225 x 1585 pixels. Because that live export failed earlier on image loading, the cropping observation itself is from a controlled fixture, not a successful live export.

Evidence: `edge-results.json`, `studocu-no-dimensions.pdf`, and `studocu-no-dimensions-page-1.png`.

### Medium: the shipped live test can pass when the user-facing export fails

Source: [real-test.mjs:16](https://github.com/nguyenquan27122005-cmd/docpress/blob/c8df165597d8a792b454d1b8c5ddc5b5d95ef219/real-test.mjs#L16), [real-test.mjs:360](https://github.com/nguyenquan27122005-cmd/docpress/blob/c8df165597d8a792b454d1b8c5ddc5b5d95ef219/real-test.mjs#L360), and [real-test.mjs:445](https://github.com/nguyenquan27122005-cmd/docpress/blob/c8df165597d8a792b454d1b8c5ddc5b5d95ef219/real-test.mjs#L445).

`real-test.mjs` launches Chrome with `--disable-extensions`, injects three main-world scripts manually, and builds a separate one-page `html2canvas`/PDF probe. It does not click the extension's export control, call its image-inlining path, save its downloaded PDF, load the isolated bridge/service worker/popup, or verify final visual completeness. Its PDF success criterion is only `pdf[0] === 37`.

The unmodified shipped test passed both targets in this audit. Adding an actual click before its custom extraction/probe exposed the public Scribd image failure, after which its own PDF probe still reported success. Its Studocu probe also chooses dimensions from the visible background image, while the real export uses the smaller fallback described above.

The test provides useful parser/provider-shape coverage, but its success does not establish that the complete extension works.

### Low: null page messages throw in the isolated bridge

Source: [bridge.js:4](https://github.com/nguyenquan27122005-cmd/docpress/blob/c8df165597d8a792b454d1b8c5ddc5b5d95ef219/bridge.js#L4).

The listener destructures `event.data` before validating that it is an object. On a supported document route, `window.postMessage(null, location.origin)` produces `Cannot destructure property 'id' of 'event.data' as it is null.` This is an input-validation error; the observed exception does not permanently disable later message handling. No privilege escalation was demonstrated.

### Low, baseline only; resolved during publication: packaged documentation and quality table differ

All eight runtime files in `doc2pdf.zip` match the baseline source byte-for-byte. The archived README differs from the repository README. The repository quality table says Balanced uses 80% JPEG quality and Light 65%, whereas [lib.js:120](https://github.com/nguyenquan27122005-cmd/docpress/blob/c8df165597d8a792b454d1b8c5ddc5b5d95ef219/lib.js#L120) uses 88% and 80%. Output is one JPEG per PDF page; it does not retain selectable text or vector objects.

The separate DocPress rename/documentation publication corrects the quality table and raster-only description, labels the live test as a provider parsing smoke test, adds the audit notice, and rebuilds the renamed ZIP from matching source documentation. These documentation/package discrepancies are historical baseline findings. The functional runtime defects above remain unchanged by that work.

## What was verified to work

The actual unpacked extension, including its service worker and main/isolated content scripts, loaded in an isolated Playwright Chromium 151.0.7922.34 profile. No existing user browser profile was used.

| Check | Observed result |
| --- | --- |
| `npm test` / `node test.mjs` | All 106 checks pass on Node 24.18.0. |
| JavaScript syntax checks | All runtime scripts and both test scripts parse with `node --check`. |
| Studocu controlled inline document | Two-page PDF downloaded, 41,386 bytes. |
| Studocu range 2 to 2 | One-page PDF downloaded, 20,934 bytes; correct second-page color/content. |
| Scribd controlled DOM document | Two-page PDF downloaded, 41,386 bytes. |
| Scribd JSONP through the actual message bridge | One-page PDF downloaded, 20,691 bytes; worker network response is a controlled fixture stub. |
| Popup setting | On/off choices survive popup reloads; live tests do not enable cookie removal. |
| Missing provider data / image HTTP 404 | Actionable error, no partial download, controls restored, temporary stage removed. |
| Cancellation while image XHR is pending | `Đã hủy`, no download, controls restored, temporary stage removed. |
| SPA navigation to search and back to a document | Widget removed and recreated. |
| Baseline distributable | All runtime files match source. |

Downloaded fixture PDFs were opened with both PyMuPDF and strict `pypdf.PdfReader`, checked for page count and dimensions, and rendered back to PNG. Visual inspection showed the expected page labels, body text, colors, and magenta image marker; pixel checks confirmed image pixels and page ordering. Their empty extracted PDF text is expected for the current raster design, not evidence of blank pages.

The bridge fixture deliberately aborts page fetch/XHR, then returns fixture JSONP from a stub of the worker's fetch for that one audit URL. The real MAIN-to-isolated relay, worker request validation, timeout/response-reading code, and conversion execute. One worker request is recorded with `credentials: include` and `redirect: error`. This proves the controlled messaging path, not successful live worker/CDN networking. No production file is changed.

## Live coverage and limits

The public targets were the exact two URLs in the shipped `real-test.mjs`. Browsing was signed out, used new temporary profiles, and did not sign in, modify access-control cookies, or bypass a paywall. The actual-click probe selected only page 1, which was already visible.

The shipped Chrome 155.0.8059.80/CDP environment could open both public pages on one run. Real-extension automation in headless Chromium was rejected or interrupted by the providers. Therefore, this audit distinguishes **actual extension + controlled fixtures** from **unchanged main-world export handler + live pages in the shipped Chrome/CDP environment**. It does not claim a fully installed-extension live smoke test passed. Provider navigation was intermittent, and a later traced run could not complete Studocu navigation.

No long-document stress test, signed-in account flow, every provider domain/browser, or access to unavailable preview pages was attempted. Static boundary inspection and existing tests show HTTPS/provider-family checks, a 5 MiB response limit and 20-second timeout in the privileged worker; this was not a comprehensive security penetration test. The ordinary main-world fetch/image paths do not inherit those worker limits.

## Reproduction and evidence

The source checkout is preserved unchanged at the baseline commit. Audit-only scripts, logs, fixture PDFs, raster previews, and temporary profiles live in the sibling `doc2pdf-evidence` directory.

```powershell
# In the baseline source checkout:
npm test
node --check content.js
node --check lib.js
node --check background.js
node --check bridge.js
node --check popup.js

# Reproduce the controlled browser findings from the repository root:
python -m pip install -r audits/2026-10-19/requirements.txt
python -m playwright install chromium
python -X utf8 audits/2026-10-19/browser_fixtures.py
python -X utf8 audits/2026-10-19/edge_cases.py

# Provider parsing smoke test; uses fixed Chrome/CDP port 9333:
npm run test:real
```

The published offline probes create fresh operating-system temporary directories for every run; all profiles and generated artifacts stay outside the checkout. They assert baseline observations, including known defects, rather than serving as release acceptance tests. See `audits/2026-10-19/README.md` for dependencies, limits, and manual live reproduction steps.

Additional local evidence includes copies of baseline `real-test.mjs`, `lib.js`, `content.js`, and `html2canvas.min.js`. The evidence-only `prepare_live_probe.py` generates a live harness that clicks the unchanged export handler before the original test mutates document image state, enables normal browser downloads, and records selected CORS network events. It does not edit the repository or alter conversion logic. Those local live logs, downloaded documents, browser profiles, and signed CDN URLs are not part of the published source artifacts.
